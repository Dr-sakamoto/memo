# 🍇 MEMO — 自分だけのCNS（Closed Network Service）

🔗 **[アプリを開く](https://dr-sakamoto.github.io/memo/)**（GitHub Pages）

日記・反省・分析・人生計画・思考ログのための、**自分ひとりのSNS**。
Xや755と同じ操作感で**雑記**を書き散らし、AIが「唯一の他者の目」として**週・月の単位で構造的に解釈**する。
1週間育てると**発芽**し、過去の自分のポストが電光掲示板のように流れてくる。

コンセプトは**一本化して醸造する**。MEMOの雑記も、X・755に書いた自分の投稿も、つぶやきレベルのアウトプットはすべて**つなげず・分けず、一本の流れに溜める**。それをAIが週・月の単位で**醸造**し、構造を引き出す。ブドウの木にとって、つぶやきは粒、醸造したレポートが房になる。

## 設計思想

**入力は構造化しない。構造はAIの解釈の側に置く。**

```
あなた: 雑に書き散らす（MEMO / X / 755 どこでもいい。つなげる・分ける判断はしない＝判断コストゼロ）
   ↓
一本の流れ: つぶやきは1件ずつ独立して時系列に溜まる（MEMOの雑記 ＋ 外部SNSの自分の投稿）
   ↓
AI（唯一の他者）: 予め決めた分析フォーマット（固定スキーマ）で週次/月次に構造化
   ↓
汎用データ: 毎回同じスキーマのJSONが蓄積 → 時間をまたいだメタ分析・他ツールへの持ち出しが可能
```

1日単位でAIは介入しない（鬱陶しいので）。AIの基本の出番は最小7日単位。

投稿どうしの連結（旧: 連＝連続投稿の自動まとめ、接ぎ木＝引用、再芽＝セルフRT）は廃止した。どの投稿がどれとつながるかは書く側が決めることではなく、醸造（AIの解釈）が見つけ出すもの、という整理。過去データの `threadId` / `refId` / `quoteCount` は消さずに保持しているので、必要になれば復元できる（過去の引用ポストは引用元を読み取り専用で添えて表示し、本文のない再芽はタイムラインに出さない）。

## 特徴

- **完全ローカル・依存ゼロ** — ビルド不要の素のHTML/CSS/JS。全データはブラウザのlocalStorageに保存。AI利用時のみ、自分のブラウザから選択したプロバイダのAPIへ直接送信（中間サーバーなし）
- **タイムライン** — 雑記を刻むだけ。気分（-2〜+2）とハッシュタグは任意
- **一本の流れ** — つぶやきは1件ずつ独立して時系列に並ぶ。連結・まとめの操作はない。気分（-2〜+2）とハッシュタグは任意
- **電光掲示板 — 忘却×偶然エンジン** — 7日間活動して発芽すると解禁。重要度では回さない（繰り返す重心ばかり流すと思考が偏り、ひらめきが生まれにくいため）。**ほぼ一様ランダム＋直近クールダウン**（最近流したものは避ける＝「同じのばっかり」を殺す）で過去の自分が流れ、**節目重力**（1年前・5年前などの「ちょうど今日」）だけ薄く残す。統合タブで取り込んだ外部SNSの自分の投稿も一緒に流れる。クリックでその日のつぶやきへ飛ぶ（外部投稿は元のページを開く）
- **時間軸ビュー** — 1週間前〜10年前の「その頃の自分」を一覧
- **ブドウの木** — 活動日数で成長：種 → 発芽(7日) → 蔓(21日) → 葉(60日) → 花(180日) → 実(365日)。つぶやきが粒、醸造したレポートが房になる
- **レポート（醸造・本丸）** — 完了した週/月の一本の流れ（MEMOの雑記＋外部SNSの自分の投稿）をAIが固定スキーマで解釈：
  - 気分スコアと推移・主要テーマ・感情の内訳・**盲点**・**矛盾**・次の一手・読み返すべき雑記・手紙
  - **レポートは前回を読む** — 前回の「次の一手」をやれたかの判定（✅/🔸/⭕️）と、先送りしている宿題（持ち越し）が毎回浮上する
  - レポートが2件以上貯まると**メタ分析**：AI観測の気分スコア推移グラフ、提案の実行率、繰り返し現れるテーマ（＝あなたの重心）の検出
  - 未作成の週があるとタイムラインに控えめなバナーで提案
- **マルチプロバイダAI** — Claude（Anthropic）/ Gemini（Google）を設定で切替。データが構造化されているのでAIは交換可能な部品。普段はGemini Flash（月数十円目安）、深く読ませたい時はClaude Opusなどの使い分けが可能
- **統合ハブ（X・755などの外部SNS）** — 外に書いた投稿とMEMOの雑記を1本のタイムラインで横断閲覧・分析・抽出。Chrome拡張（`extension/`）でX・755を閲覧するだけで集まり、Xの公式アーカイブ（`tweets.js`）で過去の全投稿も取り込める。詳細は下の「統合ハブ」節
- **エクスポート/インポート** — 雑記＋レポートをJSON一括バックアップ
- **クラウド同期（任意）** — スマホ⇔パソコンで雑記＋レポートを自動同期。自分で用意したSupabaseに接続する方式で、**中間サーバーは介さず・AIキーは同期しない**（端末ローカルのまま）。設定しなければ従来どおり完全ローカルで動く

## 使い方

ES Modulesを使っているため、ローカルHTTPサーバーで開きます：

```sh
cd memo
python3 -m http.server 8000
# → http://localhost:8000 を開く
```

### AI連携の設定

- **Claude**: [Anthropic Console](https://console.anthropic.com/) でAPIキー取得
- **Gemini**: [Google AI Studio](https://aistudio.google.com/) でAPIキー取得（低コスト）

「設定」タブでプロバイダを選びキーを保存。キーはlocalStorageにのみ保存され、ブラウザから各社APIへ直接送信されます。共有PCでは使用しないでください。

### オフライン対応（Service Worker）

`sw.js` がアプリシェル（`index.html` / `css/style.css` / `js/*.js` / `manifest.webmanifest` / `icons/`）をインストール時にプリキャッシュし、`fetch`はcache-firstで返す。データはlocalStorageのみなのでキャッシュ対象は静的資産だけであり、AI API呼び出し（`api.anthropic.com` / `generativelanguage.googleapis.com`）は`sw.js`内で明示的に除外していて常にネットワークへ素通しする。**運用ルール**: `index.html`・CSS・JS・アイコンなど、シェルの中身をデプロイで変更したら、必ず`sw.js`先頭の`CACHE_VERSION`をインクリメントすること。バージョン文字列を上げないとブラウザは`sw.js`自体の変更（バイト差分）を検知できず、古いService Workerが居座って新しいデプロイがユーザーに反映されない「更新の罠」が発生する。バージョンを上げれば、次回アクセス時に新しいキャッシュがインストールされ、`activate`時に古いバージョンのキャッシュが破棄される。

## クラウド同期 — スマホ⇔パソコン（`js/sync.js`）

**「完全ローカル・依存ゼロ・中間サーバーなし」を崩さないまま、複数端末で同じ雑記を育てる。** ライブラリを足さず、ユーザー自身が用意したSupabaseの Auth(GoTrue) と REST(PostgREST) を`fetch`で直接叩く。接続先（Project URL / 公開キー）はAI APIキーと同じく「自分で鍵を持つ」方式で設定タブに入力する。

- **セットアップ** — 既定の接続先（Supabaseプロジェクト）が `js/sync.js` に埋め込み済みで、**利用者は接続設定なしで、両端末で同じアカウントにログインするだけ**で同期が始まる。ログインしなければ従来どおり完全ローカルで動作する。自分のSupabaseに切り替えたい場合は `docs/supabase-setup.sql` の手順でプロジェクトを作り、設定タブの「接続先の設定」でURLと公開キー（anon / publishable key）を上書きする。
- **同期する対象** — 雑記＋レポートのみ。**AI APIキーやプロバイダ設定は同期しない**（センシティブなので端末ごとに保持）。
- **保存形式** — `memo_state` テーブルにユーザーごと1行、`data`(jsonb) に雑記＋レポートをまるごと保存。Row Level Security により、ログイン本人の1行しか読み書きできない（公開キーを埋め込んでも他人のデータは覗けない）。
- **マージ方針** — 端末Aと端末Bのデータを **id で突き合わせて和集合**を取る（同一idは情報量の多い方＝AI返信あり・引用/再掲が多い方を残す）。これにより**どちらの端末で書いた分も失わない**。トレードオフとして「削除」はクラウドへ伝播せず、他端末に残っていれば復活しうる（v1の割り切り）。
- **同期のタイミング** — 起動時 / データ変更時（1.5秒デバウンスの自動プッシュ）/ 画面復帰時（`visibilitychange`）。設定で自動同期をOFFにすると「今すぐ同期」ボタンのみになる。
- **オフライン整合** — Service Worker は `*.supabase.co` への通信をキャッシュ対象から明示的に除外し、常にネットワークへ素通しする。

## 統合ハブ — X・755など外部SNSの統合（`js/hub.js` / `js/hub-ui.js` / `extension/`）

**MEMOは「自分だけの場所」、X・755は「人に見せる場所」。その両方に散らばった自分を1か所で読む。** 「統合」タブに、MEMOの雑記と外部SNSの投稿を時系列で並べ、横断して検索・分析・抽出できる。

### 取り込み経路

| 経路 | 取れるもの | 備考 |
|---|---|---|
| **Chrome拡張**（`extension/`） | X: 画面に表示された投稿（本文・日時・いいね等）／ 755: **追跡リスト**に登録したトーク（アカウント）の投稿を自動取得／ 任意サイト: 選択テキスト（右クリック「MEMOハブへ送る」） | 閲覧するだけ・登録するだけで拡張に貯まり、MEMOのページを開くと自動で届く |
| **Xの公式アーカイブ** | 自分の全投稿（`data/tweets.js`、`tweets-part1.js` …） | 最も確実。X「設定 → アカウント → データのアーカイブをダウンロード」 |
| **JSON** | 拡張の書き出し・このタブのJSONエクスポート | 形式 `{format:"memo-hub/v1", items:[...]}` |

#### Chrome拡張のインストール

1. このリポジトリの `extension/` フォルダを手元に置く（ZIPでダウンロードして展開でもよい）
2. Chromeで `chrome://extensions` を開き、右上の「デベロッパーモード」をON
3. 「パッケージ化されていない拡張機能を読み込む」→ `extension/` フォルダを選択
4. 拡張のアイコンから X のユーザー名（自分の投稿の判定用）と、集める範囲（表示されたすべて／自分の投稿だけ）を設定
5. X を普段どおり見る → アイコンのバッジに未送信件数が出る → 「MEMOを開いて届ける」かMEMOのページを開くと統合タブに入る

拡張は**読むだけ**で、X・755に書き込んだりクリックしたりはしない。集めたデータはそのブラウザの `chrome.storage.local` にだけ置かれ、MEMOのページ（`dr-sakamoto.github.io/memo/` と `localhost`）以外へは送られない。ページとの橋渡しは `bridge.js`（MEMOのページに挿入されるコンテンツスクリプト）と同一オリジン内の `window.postMessage` で行い、ページが受領（ack）したものを送信済みにする。

#### 755の追跡リスト（アカウント単位）

755はユーザーごとに「トーク」（`7gogo.jp/<トークID>`）を持つので、**トーク＝アカウント**として追う。拡張のポップアップの「755 追跡リスト」で**トーク名・ユーザー名を検索**し、結果（アイコン・フォロワー数・最終更新つき）から「追加」を押す。トークIDやURLを直接入れても追加できる。追加すると:

- 初回は新しい方から最大3000件をさかのぼって取り込む
- 以降は Chrome が開いている間、**3時間おきに新着だけ**を自動で取りに行く（`chrome.alarms`）。「更新」「すべて今すぐ更新」で手動でも取れる
- トークの持ち主の名前は自動で取得。最終確認の時刻・取り込み件数・失敗理由をリストに表示
- 自分のトークIDを設定しておけば「自分の投稿」として扱われ、レポート（醸造）の材料にもなる。「自分の投稿だけ」を集める設定でも、追跡リストに登録したトークは取り込む
- 755のサイト本体がメンテナンス中で開けなくても、取得に使うAPIは応答する（2026-11 時点で確認）

使っているのは公式Webが使っているログイン不要のAPI（投稿: `api.7gogo.jp/web/v2/talks/<id>/posts`、検索: `api.7gogo.jp/web/v2/search/talks?query=<語>&offset=<n>`）で、`direction=PREV|NEXT` と `targetId`（その投稿IDを含む）でページを送る。リクエストの間は0.6〜0.8秒空けて、先方に負荷をかけない。

> ⚠️ 画面からの読み取りは、各SNSの画面構造（X の `data-testid` など）が変わると取れなくなることがある。755のAPIは公開仕様ではないため、予告なく変わる可能性がある。自分のアカウントの記録を手元に残す個人利用の範囲で使うこと。過去の全投稿を確実に残したい場合はXの公式アーカイブが最善。

### 閲覧・分析・抽出

- **絞り込み** — ソース（MEMO / X / 755 / Web）・キーワード（スペースでAND、`-語` で除外）・期間・「自分の投稿のみ」・並び順（新しい順／古い順／いいね順）
- **分析** — 絞り込んだ結果に対して、ソース別件数・月ごとの量（ソース別積み上げ）・時間帯・曜日・よく出る言葉・ハッシュタグ・よく言及する相手。言葉をタップするとその語で抽出される（依存ゼロの簡易トークナイザ: 漢字/カタカナの連続と英単語）
- **抽出** — 絞り込んだ結果をそのまま **CSV**（Excel対応のBOM付きUTF-8）/ **JSON** で書き出し
- **AIで分析** — 絞り込んだ結果（最大300件）を設定中のAI（Claude / Gemini）に渡し、テーマの移り変わり・「MEMOで書く本音とSNSで見せる顔」の違い・繰り返す関心・気づいていないパターンを横断分析
- **醸造の材料にする** — 「自分の投稿」と判定された外部投稿（リポストは除く）は、レポート生成と電光掲示板の材料として一本の流れに合流する（統合タブの設定でOFFにできる）。AIには `[X]` などの出自ラベル付きで渡すので、「自分だけの場所で書いたこと」と「人に見せる場所で書いたこと」を区別して読める。外部投稿は雑記ストアとは別に保存するため、ブドウの木の活動日数には数えない
- **𝕏 Xにも投稿** — MEMOの雑記をXの投稿画面（Web Intent）に渡す。自動投稿はせず、送信は自分で押す

### データの置き場所と同期

外部投稿は雑記とは別キー（`cns.external.v1`）に保存。クラウド同期は**既定OFF**で、統合タブの「取り込んだ外部投稿もクラウド同期する」をONにすると `memo_state.data.external` に含めて id 和集合でマージする（同じ投稿は後から取得した方＝メトリクスが新しい方を残す。削除は墓標 `deletedExternalIds` で伝播）。OFFの端末は、他端末が同期した外部投稿をリモートに素通しで保持し、消さない。

## 醸造はClaudeのルーティンに任せる（`scripts/routine/` / `docs/routine-brew.md`）

**採取はアプリ、分析（醸造）はClaudeのルーティン。** 毎週ルーティンが起動し、クラウド同期された一本の流れ（MEMOの雑記＋外部SNSの自分の投稿）を読んでレポートを醸造し、アプリへ届ける。レポートはメールなどの外の場所ではなく、**アプリのレポートタブに「🤖 ルーティン」の印つきで、他のレポートと同じカードとして並ぶ**（メタ分析・持ち越し・房もそのまま続く）。アプリ内の「生成」ボタンも残してあり、どちらで作っても同じ固定スキーマ。

```
採取（アプリ＋Chrome拡張） → 一本の流れ → クラウド同期（memo_state）
                                               ↓ 毎週（ルーティン）
     brew-fetch.mjs: 未醸造の「完了した週・月」の材料を取る（routine_read_state）
     Claude: 固定スキーマで醸造（人格は js/ai.js の SYSTEM_PROMPT と同じ）
     brew-put.mjs: アプリと同じ規則で正規化して受け取り箱へ（routine_put_report → memo_inbox）
                                               ↓ アプリの次の同期
                     受け取り箱のレポートを取り込み、memo_state に書き戻してから箱を空にする
```

- **権限は最小** — ルーティンはログインしない。アプリの「設定 → クラウド同期 → 🤖 Claudeのルーティンに醸造を任せる」で発行する**連携トークン**だけを持ち、それでできるのは「自分の memo_state を読む」「受け取り箱にレポートを置く」の2つだけ（`SECURITY DEFINER` のRPC経由）。memo_state を直接書き換えないので、同期との競合で雑記を失わない。サーバーにはトークンのSHA-256ハッシュだけを保存し、アプリで「無効化」すれば即座に使えなくなる
- **同じ他者・同じ形式** — 固定スキーマと正規化は依存ゼロの `js/schema.js` に切り出し、アプリとルーティンのスクリプトで共有。人格はアプリの `SYSTEM_PROMPT` をそのまま読み出す。「自分の投稿」の判定もアプリと同じ（判定用の設定 `hubPrefs` を同期データに含める）
- **重複しない** — 同じ期間のレポートが既にあれば（アプリ内でも生成した等）受け取り箱の分は捨てる

### セットアップ

1. Supabaseで `docs/supabase-routine.sql` を実行（受け取り箱・連携トークン・RPC）
2. アプリで同期にログインし、設定タブで**連携トークンを発行**（表示は一度だけ）
3. Claude側で、ホスト `<project>.supabase.co`・ヘッダ `x-memo-routine-token` のネットワークシークレットとしてトークンを登録
4. 週1回のルーティンを作る（指示は「`docs/routine-brew.md` に従って醸造する」）

外部SNSの投稿も醸造に混ぜるには、統合タブで「取り込んだ外部投稿もクラウド同期する」をONにする（ルーティンが読めるのは同期されたデータだけ）。

## レポートの分析フォーマット（固定スキーマ v2）

```json
{
  "mood_score": 0.4,            // -2〜+2、AIが観測した期間全体の気分
  "mood_trend": "up",           // up | flat | down
  "mood_evidence": "...",       // スコアの根拠
  "themes":   [{ "name": "...", "weight": 0.6, "summary": "..." }],
  "emotions": [{ "label": "焦り", "intensity": 3 }],
  "blind_spot": "...",          // 本人が気づいていなさそうな視点
  "contradiction": "...",       // 言動のズレ
  "suggestion": { "action": "...", "why": "..." },
  "previous_action_review": {   // v2〜: 前回の一手をやれたかの判定
    "status": "done",           // done | partial | not_done | unknown
    "evidence": "..."           // そう判定した今期の記述
  },
  "open_loops": [               // v2〜: 未解決のまま持ち越している宿題（最大5件）
    { "label": "...", "note": "..." }
  ],
  "reread_post_ids": ["..."],   // 読み返す価値のある雑記
  "letter": "..."               // 人間が読む用の手紙全文
}
```

スキーマはバージョン管理（`schemaVersion`）されており、後から観点を追加しても過去レポートは壊れない。v1のレポートは新フィールドを持たないため、表示側は `schemaVersion` を見て新セクションの描画を分岐する。

### レポートの記憶（持ち越し文脈）

v1では、AIが毎週出す「次の一手」は誰にも追跡されない**開ループ**だった。v2ではレポート生成時に、同じ粒度（週次なら週次）の直近レポートから `suggestion` と `open_loops` を取り出して**生成プロンプトの冒頭に差し込む**（`buildCarryOver()` / `js/report.js`）。AIは今期の記録を根拠に前回の一手が実行されたかを判定し、片づいていない宿題を次へ引き継ぐ。これにより「先週言われたことをやったか」「先送りしている宿題は何か」がレポートカード上に自動で浮上し、メタ分析には**提案の実行率**（v2以降のレポートのみを対象）が出る。

## 整形ワークフロー — 無料枠でも無造作なログを高精度データに（`js/workflow.js`）

**「入力は構造化しない」思想の裏側で、構造化そのものを担うのがこの多段パイプライン。** 無秩序に書き散らした雑記を、Geminiの無料枠のままでも取りこぼしなく固定スキーマへ落とし込むために、1レポートの生成を「小さく分けて抽出 → まとめて統合」の map-reduce に分解している。

```
Stage 0  正規化 （ローカル・無API）: 時系列整列・空/重複除去・チャンク分割
Stage 1  抽出   （map / AI）        : 各チャンク → 原子的な「観測ユニット」（根拠ポストID付き）
Stage 2  統合   （reduce / AI）      : 観測ユニット全体 → 固定スキーマ（REPORT_SCHEMA）
Stage 3  照合   （ローカル・無API）: スコアのクランプ・IDの実在検証・トピック頻度の付与
```

- **観測ユニット**（`{ ids, observation, topic, emotion, valence }`）— 無造作なつぶやきを、脚色しない原子的な事実へ分解する中間表現。長い期間を一撃で要約させるより取りこぼしが減り、各根拠が元ポストのIDに紐づくため後段の統合がブレにくい。
- **無料枠オーケストレーション**（`js/ai.js` の `callAIPaced`）— 多段化でAPI呼び出しが増えるぶん、全呼び出しを直列化して**毎分レート上限（RPM）を守る間隔**を自動で空け、`429`/`503` では**指数バックオフ**で自動リトライする（Geminiの`RetryInfo`・`Retry-After`があれば優先）。「用意されたワークフローをこなせば」無料枠のままでも生成が完走する。
- **生成モード（設定で切替）** — `自動`（長い期間だけ多段解析。既定）/ `常に多段解析`（最高精度・API回数増）/ `常に一括`（API 1回・無料枠を最大限節約）。短い期間は一括（API 1回）に自動フォールバックする。
- **照合（Stage 3）** — AIのブレを固定スキーマへ寄せる安全化。気分スコアは-2〜+2にクランプ、`reread_post_ids`は実在するポストIDだけに絞り込む。これにより毎回同じ形の**汎用データ**が保証され、レポート横断のメタ分析が安定する。

各レポートには生成の来歴（`pipeline`: モード / 分割数 / 観測ユニット数 / API呼び出し回数）が記録され、レポートカードにも表示される。

## アルゴリズム（過去設計「ワタアメ宇宙」からの移植）

掲示板の抽選は重要度から切り離す（v2でのリファイン）。投稿どうしの連結（連・接ぎ木）はv3で廃止し、つながりの発見は醸造（AI）側に寄せた。

| 概念 | 本アプリでの実装 |
|---|---|
| 一本の流れ | つぶやきは1件ずつ独立（`threadId` / `refId` は新規投稿では常に null）。MEMOの雑記と外部SNSの自分の投稿を時系列で合流させたものが醸造プール（`brewPool()` / `js/report.js`） |
| 房 | 醸造したレポートの数（週次・月次・四半期・年次）。旧仕様の「引用された回数」ではない |
| 掲示板の抽選 | ほぼ一様ランダム。**直近クールダウン**で「同じのばっかり」を避け、**節目重力だけ薄く**（`ANNIVERSARY_STRENGTH`）効かせる |
| 節目重力 | 経過日数が 7日/30日/90日/1年/5年/10年 の節目に近いほど引かれる（掲示板では薄めて使用、「◯年前の自分」ラベルにも流用） |
